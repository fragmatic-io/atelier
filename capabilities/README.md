# capabilities/

Typed action and data definitions — the **public surface** of a CIR app. Each capability declares its input, output, side effects, permissions, confirmation policy, rate limit, and reversibility. Capabilities are signed, versioned, and edge-cached. The compiler reads them; the runtime never invokes them directly.

## Files

- **Format**: JSON Schema
- **Naming**: `{domain}/{name}.json` — e.g. `thread/archive.json`, `task/create.json`
- **One capability per file.** Domains group related actions and data resources.

See [`../docs/artifacts.md`](../docs/artifacts.md) — section "Capabilities + Skills (PUBLIC)" for the full schema and the worked `thread.archive` example.

## Adding a capability

Follow [`../AGENTS.md`](../AGENTS.md) — section "When asked to add a capability". In short:

1. Define the schema at `/capabilities/{domain}/{name}.json`.
2. Write the matching skill at `/skills/{name}.skill.md`.
3. Add **at least 3 eval cases** at `/evals/capabilities/{name}.eval.json`.
4. Advertise the capability in `/.well-known/cir.json`.
5. Bump the registry version.
6. **Do not write any UI.** UI is generated by the compiler.

Every capability MUST honestly declare `side_effects`, `permissions`, and `reversibility`. Any change to input, output, or side effects requires a **version bump** and a migration note (see Hard Rule 2 in `AGENTS.md`). Old manifests pinned to old versions must keep working for the deprecation window (default 90 days).
