> **Capabilities and skills are the public artifact.**
> **Intent is the private artifact.**
> **UI is ephemeral output.**

Software ships **capabilities and skills** (typed actions, data, usage knowledge). Users keep **intent** (preferences, lenses, rules). Agents emit **operational UI as ephemeral output** — a `Manifest` JSON document the runtime renders. Cached. Versioned. Recomputed only on trigger.

Atelier is the integration of pieces that already exist — MCP-style capabilities, skills, JSON manifest UI, intent profiles, multi-tier caching, pub-sub triggers — into one principled architecture. **Compile rarely, render constantly.**

The product promise is deliberately bounded: **operational UI generated from
capabilities, policies, intent, and a strong component/composition system.**
Atelier is not a prompt-to-any-app generator. It is for support ops,
sales/revenue ops, marketplace ops, compliance/risk ops, and engineering ops
teams that need role-specific workbenches over the same systems of record.

## The operational-ui pivot

**Wave M, 2026-05-02.** The framework proved the baseline-first direction: three reference apps, different domains, **zero custom React components.** The next promise is stricter: primitives are necessary but not enough. Atelier must pair mature primitives with composition rules and operational composites that make generated workbenches feel useful, auditable, and on-brand.

|          |                       |
| -------- | --------------------- |
| Aurora   | **0** custom bindings |
| Octant   | **0** custom bindings |
| Marigold | **0** custom bindings |

A demo's custom-binding count is one smell test for whether the framework's catalog promise is being kept. The stronger test is whether a generated operational workflow can take a real user from context → decision → policy-confirmed action → audit record without handwritten route UI. The [ETHOS principle #11](/atelier/introduction/ethos/) codifies the baseline-first rule; the [product promise](/atelier/introduction/product-promise/) codifies the narrower market promise.

> **Naming note.** Two distinct things in this codebase share the word "marketplace":
>
> - **The catalog** — the set of baseline primitives shipped by `@atelier/components`. This is the _product_.
> - **The vault marketplace** — the distribution channel (`atelier://author/persona@version`, ed25519 signing, TOFU). This is V-6 in Wave 8 and is partially shipped.
>
> When we say "marketplace" alone we mean the distribution channel.

## Compile rarely. Render constantly.

One LLM call on the cold path (≈ 5–20k tokens). Zero LLM calls on the hot path. Triggers — capability bumped, intent changed, component removed, user-requested recompile — are the only things that invalidate. Everything else is a pure function of `(manifest, data)`.

[See the architecture →](/atelier/architecture/)

## First audience

Atelier is aimed first at ops-heavy organisations with many internal-tool
variants: support ops, sales/revenue ops, marketplace ops, compliance/risk ops,
and engineering/platform ops. These teams already pay for internal software.
The pain is maintaining role-specific queues, dashboards, review flows, and
action surfaces over the same systems of record.

The wedge is not "replace every app builder." It is **policy-safe, per-workflow
interfaces over a stable capability surface**.
