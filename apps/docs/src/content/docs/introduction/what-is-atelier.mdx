Atelier is a **product brand** built on the **CIR architectural pattern**:

- **C**apability — typed actions and data the app exposes (signed, versioned, public).
- **I**ntent — the user's lenses, vocabulary, density preferences, rules (private, durable, vault-stored).
- **R**ender — a `Manifest` JSON document produced by an LLM compiler, walked by a dumb client, cached, versioned, recomputed only on trigger.

Both names appear in this documentation. **Atelier** is what you ship; **CIR** is the architectural shorthand you use when explaining how the pieces fit together.

## The one-line thesis

Software ships **capabilities and skills**. Users keep **intent**. Agents emit **operational UI as ephemeral output** — cached, versioned, recomputed only on trigger.

The first is public, signed by the company, versioned like a database schema. The second is private, durable, owned by the user, portable across apps. The third is disposable — a manifest the runtime renders, never the source of truth. "UI" here means any rendered surface: a web page, a native screen, an inline chat component, a voice prompt, a spatial overlay.

Get this separation right and the flexibility problem for operational software becomes tractable: one capability surface, many policy-safe interfaces, recomputed only when the work context actually changes.

## Target organisation

The first buyer is not "anyone who wants generated UI." It is an operational
organisation drowning in internal-tool variants: support ops, sales/revenue
ops, marketplace ops, compliance/risk ops, and engineering/platform ops. These
teams already have systems of record and internal app builders. Their problem
is that each role, region, queue, or review workflow wants a different screen,
and maintaining those screens becomes its own product surface.

Atelier's wedge is to define the capability surface once, validate every
manifest against policy, and compile the interface per role/workflow instead of
forking the frontend.

## Product promise

Atelier's promise is **operational UI generated from capabilities, policies,
intent, and a strong component/composition system**.

This is narrower than "fully dynamic UI" or "any app from a prompt." The first
production-grade surfaces should be workbenches for queues, reviews,
exceptions, approvals, account context, policy obligations, reversible actions,
and audit trails. If a workflow has real systems of record, role-specific
screens, and safety requirements, it belongs in Atelier's first market. If it
is a consumer landing page, a canvas editor, a game, or a bespoke brand
experience, it does not.

## The five public artifacts

These are owned by the app. Signed. Versioned. Cacheable at the edge.

- **Capabilities** (`@atelier/schemas` `CapabilitySchema`) — typed actions + data resources.
- **Skills** (markdown with YAML frontmatter) — usage knowledge, when-to / when-not-to-use.
- **Components** (`@atelier/components`) — 83 baseline React primitives plus per-component metadata.
- **Policies** (`@atelier/policies`) — pure-function validators, baseline + custom.
- **Brand kit** (`BrandTokensSchema`) — design tokens, typography, density, motion, voice.

## The one private artifact

- **Intent profile** (lives in the vault) — the user's lenses, vocabulary, rules, density preference, dark-mode preference, cross-app workflows. Apps request scoped read access; never write.

## The ephemeral output

- **Manifest** — JSON tree. Compiled once on cold path; cached at three tiers (server `ManifestStore`, browser memory, browser IndexedDB). The runtime walks it. The renderer maps node IDs to registered `ComponentBinding`s. Actions dispatch through the `ActionDispatcher` (modal confirm, optimistic UI, undo).

## The catalog promise

Atelier's catalog wager: **give the compiler mature primitives, strict
composition rules, brand tokens, and reusable operational composites, and it can
produce useful domain workbenches without per-host React.** No bespoke
`IssueQueue` / `ProductCard` / `ThreadView` bindings for every app.

That promise is verifiable. The three reference demos — Aurora (productivity),
Octant (GitHub issues), Marigold (e-commerce) — all ship **zero custom
bindings** as of the marketplace pivot (Wave M, 2026-05-02). Custom-binding
count remains a useful smell test, but the product test is stronger: can a
generated surface complete a real operational loop from context → decision →
policy-confirmed action → audit?
