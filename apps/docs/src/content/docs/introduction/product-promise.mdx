## Promise

Atelier is pursuing one specific product promise:

**Operational UI generated from capabilities, policies, intent, and a strong
component/composition system.**

That is the line. Not "fully dynamic UI for every product." Not "generate any
app from a prompt." Atelier is for teams whose work already lives in systems of
record and whose pain is the number of internal interfaces they maintain over
the same actions, data, permissions, and policies.

## First buyer

The first buyer is an ops-heavy organisation with many internal-tool variants:

- support ops
- sales/revenue ops
- marketplace ops
- compliance/risk ops
- engineering/platform ops

These teams already pay for Retool-style apps, custom admin panels, BI tools,
and workflow automation. They do not need another way to draw a button. They
need a way to define capabilities and policies once, then get role-specific
workbenches that stay safe, auditable, and on-brand.

## What good looks like

A generated Atelier surface is useful only if it completes an operational loop:

1. **Context** — show the relevant account, queue, issue, order, alert, or case.
2. **Decision** — highlight the few facts that change what the operator should do.
3. **Policy** — expose confirmations, restrictions, and required grants before action.
4. **Dispatch** — call typed capabilities through the `ActionDispatcher`, not local component code.
5. **Audit** — record compile, policy validation, action attempt, result, and rollback/undo.

This is the bar for production demos. A pretty component catalog is not enough.

## Non-goals

Atelier should not claim:

- arbitrary dynamic UI for every software category
- consumer marketing pages or landing pages as a primary use case
- canvas-heavy creative tools, games, or real-time multiplayer editors
- free-form generated React/HTML in production
- replacing design systems
- replacing Retool immediately in every internal-tool scenario

Atelier can integrate with mature primitive libraries and brand systems. Its
own value lives in the capability, policy, intent, manifest, composition,
runtime, trigger, and audit layers.

## Component strategy

Low-level primitives should come from mature behavior libraries where possible:
dialogs, drawers, menus, popovers, selects, tabs, tooltips, command palettes,
focus management, keyboard navigation, portals, and outside-interaction
handling.

Atelier should own:

- manifest-facing props and data attributes
- component metadata and composition rules
- brand-kit token integration
- policy-aware action slots
- visual and interaction Storybook checks
- operational composites such as review workbenches, context panels, approval
  centers, audit timelines, exception queues, and policy gates

The question for every component PR is: does this make generated operational
UI more trustworthy, more useful, or more on-brand?

## Pilot plan

### 1. Mature the interaction primitives

Migrate the remaining high-risk primitives onto mature behavior foundations:

- `Select`
- `Tabs`
- `Tooltip` / `Popover`
- `CommandPalette`

Each migration must keep Atelier's manifest-facing contract stable and ship a
Storybook interaction test.

### 2. Add operational composites

Add a small set of domain-agnostic operational composites:

- `ExceptionReviewWorkbench`
- `CustomerContextPanel`
- `ApprovalCommandCenter`
- `PolicyAuditTimeline`

These should be composed from baseline primitives where possible, but promoted
to baseline when the pattern appears across demos and the compiler needs a
stable vocabulary.

### 3. Prove one golden workflow

Ship one golden end-to-end Storybook/demo path:

`capability → manifest → rendered workbench → policy-confirmed action dispatch → audit event`

The workflow must run without custom route UI and without hand-authored
manifests as the primary path.

### 4. Gate quality

Production readiness requires gates, not taste:

- schema validation at resolver level
- policy validation hard to omit
- validation provenance for tool-using compilers
- Storybook visual and interaction checks for default brand presets
- smoke tests for publishable packages and CLIs
- audit assertions for every action path

### 5. Sell the wedge

Position the first paid pilot around one operational pain:

> "Your team has too many role-specific dashboards over the same systems. Define
> capabilities and policies once; Atelier generates safe, auditable workbenches
> per workflow."

If that pitch resonates, expand. If it does not, do not widen the promise. Fix
the workflow proof.
