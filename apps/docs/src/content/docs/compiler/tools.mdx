The tool-using compiler exposes ten tools to the LLM agent. The agent calls them via Gemini's function-calling protocol. The host provides the registry data and optional resolver hooks through a `ToolEnvironment`.

## The ten tools

| Tool                      | Purpose                                                                    | Phase |
| ------------------------- | -------------------------------------------------------------------------- | ----- |
| `lookupCapability`        | Get a capability's full schema by id.                                      | C-2   |
| `findCapability`          | Substring / semantic search across the capability registry by description. | C-2   |
| `listCapabilities`        | Flat list of all capability ids and one-line summaries (used for scoping). | C-2   |
| `findComponent`           | Search the component catalog by hint ("queue with grouping").              | C-2   |
| `inspectComponent`        | Get a component's full prop schema, composition rules, slot contracts.     | C-2   |
| `listComponents`          | Flat list of all 83 baseline components.                                   | C-2   |
| `validateDraft`           | Run the draft manifest through the policy engine; return ok or violations. | C-2   |
| `inspectExistingManifest` | Read a prior manifest for the same user/route (cross-route coherence).     | C-2   |
| `listSiblingRoutes`       | List the other routes in the recipe (so chrome / nav stay consistent).     | C-2   |
| `findRecipe`              | Retrieve persona/recipe scaffolds via `@atelier/recipe-resolver`.          | C-5   |

One more is deferred:

- `explainViolation` — rolled into the violation strings the validator already returns.

## The `ToolEnvironment` interface

```ts
import type { Capability, ComponentDefinition, Manifest } from '@atelier/schemas';
import type { RecipeResolver } from '@atelier/recipe-resolver';

export interface ToolEnvironment {
  capabilities: Record<string, Capability>;
  components: ComponentDefinition[];
  validate?: (draft: Manifest) => Promise<{ ok: true } | { ok: false; violations: string[] }>;
  inspectExistingManifest?: (input: { user_id: string; route: string }) => Promise<Manifest | null>;
  listSiblingRoutes?: (input: { recipe_id: string }) => Promise<string[]>;
  recipeResolver?: RecipeResolver;
}
```

The default lookup/search behavior is intentionally simple: the compiler searches the supplied capability map and component array. Hosts swap in larger-scale retrieval by constraining the capability set before compile, by providing `recipeResolver`, or by wrapping the compiler with `TwoStageCapabilityResolver`.

## Code: a custom tool environment

```ts
import { createBaselineManifestValidator } from '@atelier/compiler';
import type { ToolEnvironment } from '@atelier/compiler';

const env: ToolEnvironment = {
  capabilities: loadCapabilities('./capabilities'),
  components: COMPONENT_BINDINGS_METADATA,
  validate: createBaselineManifestValidator({
    grantedFields: (input) => loadGrantedFields(input.user_id),
  }),
};

// For very large registries, scope capabilities before calling compile:
const scoped = await capabilityResolver.resolve({
  query: recipe.description,
  grantedCapabilityIds: recipe.capabilities,
  limit: 30,
});
env.capabilities = Object.fromEntries(scoped.map((capability) => [capability.id, capability]));
```

This is the seam C-3 (capability scoping) and C-5 (marketplace RAG) plug into. The substring fallback ships out of the box; production deploys swap in vector search when registries grow past ~1000 capabilities.

## Tool declarations to the LLM

The compiler ships these as Gemini function declarations:

```ts
const TOOL_DECLARATIONS = [
  {
    name: 'lookupCapability',
    description:
      'Get a capability schema by id. Use this when the recipe grants a capability and you need its full input/output/permissions.',
    parameters: {
      type: 'object',
      properties: { id: { type: 'string' } },
      required: ['id'],
    },
  },
  {
    name: 'findComponent',
    description:
      'Search the component catalog by a free-form hint. Returns up to 5 candidate components with summaries.',
    parameters: {
      type: 'object',
      properties: { hint: { type: 'string' } },
      required: ['hint'],
    },
  },
  // ... (full list in @atelier/compiler/src/tool-using-compiler.ts)
];
```

## Validation as a tool

`validateDraft` is the most interesting one. It's the same policy engine that gates the final emit, exposed as a tool the LLM can call _during_ composition:

```text
agent: I'll draft a layout with <Stack> + <Queue> + <Card>...
agent (tool call): validateDraft({ ...draft })
tool reply: { ok: false, violations: ['reversibility_surfaced: thread.archive lacks undo affordance'] }
agent: Right — I'll add the ambient UndoToast satisfier or include a manifest <Toast variant="undo"> node.
agent (tool call): validateDraft({ ...patched_draft })
tool reply: { ok: true }
agent: Final answer: { manifest: ... }
```

This is the same loop Wave C-1's `ValidationFeedbackCompiler` runs externally, but now the LLM can fix issues mid-compose without needing the wrapper. In production mode, `ToolUsingCompiler` also enforces validation provenance: the final answer must match a draft that passed `validateDraft` (ignoring server-assigned `manifest_id`). Hosts can only bypass that guard with an explicit test-only option.

## Substring fallback for C-5

Today's `findCapability` and `findComponent` fall back to substring search across descriptions. This is the seam C-5 RAG swaps in for: replace the substring matcher with a vector-search-backed alternative once recipes are vector-indexed in the marketplace.

## Showcase

The demo runs the tool-using compiler **by default**. Opt out via `ATELIER_COMPILER_TOOLS=off`; legacy `CIR_COMPILER_TOOLS_ENABLED=0` is honoured for one release cycle:

```bash
# Default — tool-using compiler is on:
pnpm --filter @atelier/demo dev

# Disable for the deterministic single-shot path:
ATELIER_COMPILER_TOOLS=off pnpm --filter @atelier/demo dev
```

The audit stream shows every tool call:


## Bounded step limit

The agent loop has a hard step ceiling (default 8 tool-call rounds, configurable). If the agent doesn't converge — keeps calling tools without emitting — the wrapper throws `CompilerOutputError`, which cascades through `CompositeCompiler` to the deterministic fallback. Users never see a stuck UI.
