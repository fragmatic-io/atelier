---
title: Validation feedback (C-1)
description: Re-prompt the same LLM with the policy violations and ask it to patch.
---

Wave C-1 is the biggest single-day win in the compiler track. When a manifest violates a policy, the framework re-prompts the SAME LLM with `{draft, violations}` and asks it to patch. Bound to 2-3 retries before cascading to `GenericFallbackCompiler`. Track via the existing `compile.budget_used` audit event so visibility is preserved.

## Why this matters

Before C-1: the compiler emitted a manifest, the validator caught a violation (e.g. "reversibility_surfaced: thread.archive lacks undo affordance"), and the chain cascaded to `GenericFallbackCompiler`. The LLM never saw its own mistake. The deterministic fallback rendered.

After C-1: the validator's violations go back into the prompt. The LLM gets a chance to patch — most of the time it does. The fallback is the safety net, not the routine path.

## The wrapper

```ts
import { ValidationFeedbackCompiler } from '@atelier/compiler';

const compiler = new ValidationFeedbackCompiler(
  new GeminiCompiler({ apiKey: process.env.GEMINI_API_KEY! }),
  {
    maxRetries: 2,
    onRetry: (attempt, violations) => {
      console.log(`retry ${attempt}: ${violations.length} violations`);
    },
  },
);

const result = await compiler.compile({ recipe, intent, route: '/today' });
//   result.attempts === number of compile attempts (1 = first try worked)
//   result.token_cost === cumulative tokens across all attempts
//   result.duration_ms === cumulative duration across all attempts
```

`ValidationFeedbackCompiler` mirrors the `BudgetMeteredCompiler` wrapper pattern from S-6. New `priorDraft` + `violations` fields land on `CompileInput`; the refinement-prompt path lives in `prompts/builder.ts`.

## The retry loop

```text
attempt 1
  → compiler emits draft_1
  → validator: violations=['reversibility_surfaced ...']
  → not exhausted? retry
attempt 2
  → compiler emits draft_2 with priorDraft=draft_1, violations=[...]
  → validator: ok
  → return draft_2 with cumulative tokens + duration
```

If `maxRetries` exhausts and the validator still says violations, `ValidationFeedbackCompiler` throws `CompilerOutputError`. `CompositeCompiler` then cascades to the next compiler in the chain (typically `GenericFallbackCompiler`). The user never sees a broken UI.

## What the refinement prompt looks like

Roughly (pseudo-text — not literal Markdown fences):

```text
SYSTEM
  Atelier framework explanation, manifest schema, validation rules.

USER
  The manifest you produced was rejected by the policy engine.

  Your prior draft was the previous JSON body.

  Violations:
  - reversibility_surfaced: thread.archive lacks undo affordance.

  Patch the manifest to address these violations.
  Return only the new manifest JSON, no commentary.
```

The compiler reads the prior draft as exemplar context and patches what's wrong. Most of the time the second attempt is correct. After `maxRetries` (default 2), the wrapper gives up and throws.

## Cumulative token tracking

```ts
// CompileOutput.token_cost is cumulative across attempts
const result = await compiler.compile(input);
console.log(result.token_cost);
//   first attempt: 11_423 tokens
//   second attempt: 4_120 tokens (refinement prompts are smaller)
//   reported: 15_543
```

This matters for budget enforcement (S-6). `BudgetMeteredCompiler` reads `token_cost` and decrements the user's daily allowance accordingly.

## Tool-using compiler integration

The C-2 tool-using compiler can call `validateDraft` mid-compose. So C-1's wrapper now has two roles:

1. **Pre-C-2:** the only validation surface. Catches every violation; retries.
2. **Post-C-2:** the post-hoc safety net. The agent already self-corrected via `validateDraft` calls; the wrapper catches anything that slipped past.

In practice, with C-2 enabled, `ValidationFeedbackCompiler` rarely retries. When it does, it's a sign the agent prompt or tool descriptions need tightening.

## Cascade through Composite

```ts
import { CompositeCompiler } from '@atelier/compiler';

const compiler = new CompositeCompiler([
  new ValidationFeedbackCompiler(
    new ToolUsingCompiler({
      inner,
      env: { capabilities, components, validate },
    }),
    { maxRetries: 2 },
  ),
  new GenericFallbackCompiler(),
]);
```

The cascade order is intentional: try the LLM compiler with retries first, fall through to the fallback only when the LLM compiler exhausts.

## Audit events

```text
compile.started        compiler=ValidationFeedbackCompiler
compile.tool_call      name=validateDraft  result=violations
compile.refinement     attempt=2  prior_violations=1
compile.completed      tokens=15543 duration_ms=4823 attempts=2
```

`<CompileBadge>` in the demo surfaces `attempts > 1` as a small annotation so the developer can see when refinement fired.

## Pitfalls

- **`maxRetries: 0` defeats the point.** Don't set it to zero; if you're concerned about cost, use `BudgetMeteredCompiler` instead — it gives you a per-user ceiling that captures more than just retry-cost.
- **Shaping the violation strings matters.** A vague "policy failed" tells the LLM nothing. Good policies return concrete, actionable violation messages. Look at how `BASELINE_POLICIES` phrase theirs.
- **Don't catch `CompilerOutputError` upstream of the cascade.** The `CompositeCompiler` chain is meant to handle it. If you swallow the error, the fallback never gets a chance to render.
