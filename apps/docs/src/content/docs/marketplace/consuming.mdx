This page walks a consumer through fetching, verifying, and installing a marketplace bundle.

## What you're consuming

A `SignedBundle` from a publisher you may or may not have interacted with before. Your job:

1. Verify the signature.
2. Reconcile against your TOFU cache (or a pinned fingerprint).
3. Inspect the recipe + scopes.
4. Walk the user through consent.
5. Install.

## The walkthrough

<Steps>

1. **Resolve the address.**

   ```ts
   import { parseMarketplaceAddress } from '@atelier/schemas';

   const address = parseMarketplaceAddress('atelier://acme/founder-inbox@1.0.0');
   ```

   `parseMarketplaceAddress` validates the URI shape and throws on malformed input.

2. **Fetch the bundle.**

   ```ts
   import { MarketplaceClient, LocalStorageTrustedKeyStore } from '@atelier/vault-client';

   const client = new MarketplaceClient({
     vaultUrl: 'https://vault.example',
     trustedKeys: new LocalStorageTrustedKeyStore(),
   });

   try {
     const payload = await client.fetch(address);
     console.log(payload.recipe); // RecipeSchema-shaped
     console.log(payload.skills); // Array of skills
   } catch (err) {
     // Three possible errors:
     //   SignatureMismatchError       — signature didn't verify
     //   MarketplaceTrustError        — TOFU mismatch (key rotated)
     //   MalformedBundleError         — bundle structure invalid
     handle(err);
   }
   ```

   The `client.fetch` flow:
   1. `GET /vault/marketplace/<author>/<persona>@<version>` from the vault (legacy route — `MarketplaceClient` continues to use it).
   2. Verify the signature locally.
   3. Check the TOFU cache — record on first contact, throw `MarketplaceTrustError` on mismatch.
   4. (If `?signed_by=` was present) check the pin matches `bundle.key_id`.
   5. Return the payload.

   **V-6.b new endpoints** (used by host-side fetchers / browse UI):

   ```bash
   # Exact version — content-addressed, immutable, long max-age cache.
   GET /marketplace/persona/<author>/<persona>@<version>
   # → 200 SignedBundle (or 404)

   # Latest semver for the (author, persona) pair.
   GET /marketplace/persona/<author>/<persona>/latest
   # → 200 { address, bundle }  (or 404 when no versions exist)
   ```

   The `/latest` response is wrapped in `{ address, bundle }` so the
   caller can distinguish the resolved version from the bundle bytes
   (the address is what the consumer pins in their TOFU store).
   `Cache-Control` on `/latest` is short + must-revalidate; on the
   exact-version route it's `max-age=31536000, immutable`.

3. **Inspect the recipe.**

   ```ts
   const { recipe, skills } = payload;
   console.log('Persona:', recipe.persona);
   console.log('Capabilities granted:', recipe.capability_grants);
   console.log(
     'Skills bundled:',
     skills.map((s) => s.name),
   );
   ```

   This is what your consent UI needs to surface. The user is about to grant scopes for these capabilities; they should see them.

4. **Present consent.**

   ```tsx
   function ConsentScreen({ recipe, skills, onApprove, onDeny }) {
     return (
       <Modal>
         <h2>Install {recipe.persona}?</h2>
         <p>{recipe.description}</p>
         <h3>Capabilities granted</h3>
         <ul>
           {recipe.capability_grants.map((c) => (
             <li key={c}>{c}</li>
           ))}
         </ul>
         <h3>Skills</h3>
         <ul>
           {skills.map((s) => (
             <li key={s.name}>
               {s.name} — {s.description}
             </li>
           ))}
         </ul>
         <ButtonGroup>
           <Button variant="ghost" onClick={onDeny}>
             Cancel
           </Button>
           <Button variant="primary" onClick={onApprove}>
             Install
           </Button>
         </ButtonGroup>
       </Modal>
     );
   }
   ```

5. **Install.**

   ```ts
   import { installRecipeBundle } from '@atelier/runtime';

   await installRecipeBundle({
     recipe: payload.recipe,
     skills: payload.skills,
     brandKit: payload.brand_kit,
     services: yourCirRuntimeServices,
   });
   ```

   `installRecipeBundle`:
   1. Writes the recipe to `recipes/<persona>.json`.
   2. Writes the skills to `skills/<name>.skill.md`.
   3. Writes the brand kit (if any) to `brand_kits/<persona>.json`.
   4. Refreshes the runtime services so the next compile sees the new files.
   5. Emits `recipe.installed` on the trigger bus so any subscriber can react.

6. **Trigger a recompile.**

   ```ts
   await services.triggerBus.publish({
     type: 'user.recompile_route',
     user_id,
     route: '/today',
   });
   ```

   The browser refetches; the new manifest reflects the just-installed recipe.

</Steps>

## Pinned fetch

For high-stakes deployments where the consumer wants explicit-key-pinning rather than TOFU:

```ts
const pinnedAddress = parseMarketplaceAddress(
  'atelier://acme/founder-inbox@1.0.0?signed_by=8f3a2b1c4d5e6f70',
);

const payload = await client.fetch(pinnedAddress);
//   bypasses TOFU; throws MarketplaceTrustError on fingerprint mismatch.
```

The TOFU cache is not consulted; not updated. The pinned fingerprint is the source of truth.

## TOFU cache management

```ts
const knownAuthors = await client.trustedKeys.list();
//   [{ author: 'acme', key_id: '8f3a2b1c4d5e6f70' }, ...]

await client.trustedKeys.delete('acme');
//   forget acme's fingerprint; next fetch re-establishes TOFU.

await client.trustedKeys.set('acme', '8f3a2b1c4d5e6f70');
//   pin acme to a specific fingerprint manually.
```

Useful when:

- A user wants to "reset trust" with an author whose key has rotated.
- Bootstrapping a new consumer with a curated allowlist (see [TOFU → Strict posture](/marketplace/tofu/#strict-posture-fail-closed-on-first-use)).

## Errors and how to surface them

| Error                    | UX surface                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `MalformedBundleError`   | "This bundle is malformed and can't be installed." (rare; usually a vault bug)               |
| `SignatureMismatchError` | "This bundle's signature didn't verify. Don't install." (serious — possible tampering)       |
| `MarketplaceTrustError`  | "This author's signing key changed. Inspect both fingerprints out-of-band before accepting." |
| Network errors           | "Couldn't reach the vault. Try again later."                                                 |

## CLI surface

```bash
# Publish (V-6.f — shipped):
pnpm atelier marketplace publish bundle.json \
  --author acme \
  --key ~/.atelier/keys/acme.private.pem

# Review / curate (V-6.d — shipped):
pnpm atelier marketplace review atelier://acme/founder-inbox@1.0.0 \
  --state approved \
  --reviewer maint-a \
  --key ~/.atelier/keys/maint-a.private.pem \
  --notes "LGTM after security pass."
```

The consume / install / trust subcommands remain roadmap:

```bash
# Roadmap:
pnpm atelier marketplace fetch atelier://acme/founder-inbox@1.0.0
pnpm atelier marketplace install atelier://acme/founder-inbox@1.0.0
pnpm atelier marketplace trust list
pnpm atelier marketplace trust set <author> <key_id>
pnpm atelier marketplace trust delete <author>
```

## Curated browse index (V-6.d)

`GET /marketplace/index` is the default browse surface. It returns
listings whose latest review state is `approved`. Direct-address fetches
still resolve unreviewed bundles (`pending`, `rejected`, `flagged`) so
authors can preview their own work — only the index hides them.

```ts
import { listMarketplace } from '@atelier/vault-client';

// Default: approved-only.
const approved = await listMarketplace(client, { domain: 'productivity' });

// Maintainer view: also include pending + flagged bundles.
const queue = await listMarketplace(client, {
  include: ['pending', 'flagged'],
});
```

Each listing carries a `reviewState` field. `<MarketplaceBrowser>` renders
a small pill for any state other than `approved` (so the default flow stays
visually quiet — see [Browse UI](#browse-ui--marketplacebrowser) below).

To inspect the curation state of a single address:

```ts
import { fetchReview } from '@atelier/vault-client';

const record = await fetchReview(client, 'atelier://acme/founder-inbox@1.0.0');
if (record === null) {
  // No review record exists. (Should not happen for published bundles —
  // publish auto-creates one. Treat as `pending` for UX purposes.)
} else if (record.state === 'flagged') {
  // Under review. Surface a warning before installing.
}
```

## Browse UI — `<MarketplaceBrowser>`

For hosts that want a drop-in browse / search / preview surface, `@atelier/components` ships a baseline primitive that consumes any `MarketplaceClient` (the `@atelier/vault-client` is the canonical implementation; tests + docs-site previews can use `MockMarketplaceClient`).

```tsx
import {
  MarketplaceBrowser,
  MockMarketplaceClient,
  type MarketplaceListing,
} from '@atelier/components';

const sample: MarketplaceListing[] = [
  {
    address: {
      scheme: 'atelier',
      author: 'acme',
      persona: 'founder-inbox',
      version: '1.0.0',
      raw: 'atelier://acme/founder-inbox@1.0.0',
    },
    description: 'Inbox lens for founders.',
    domain: 'productivity',
    brandKitId: 'acme-default',
    publishedAt: '2026-05-01T12:00:00Z',
    authorDisplayName: 'Acme',
  },
];

export function BrowsePage() {
  const client = new MockMarketplaceClient(sample);
  return (
    <MarketplaceBrowser
      client={client}
      selectCapability="marketplace.install"
      onSelect={(listing) => {
        console.log('User picked', listing.address.raw);
      }}
    />
  );
}
```

The component renders:

- A left **filter panel** (author / domain / brand kit / search). Search is debounced ~200 ms.
- A right **listings panel** (scrollable). Each card shows persona name + version pill + author + a 2-line description + domain / brand-kit chips.
- A **review-state pill** on every card whose `reviewState` is NOT `approved` (V-6.d). The default state is `approved` and showing a pill on every card is noise — the pill only renders for `pending` / `rejected` / `flagged`.
- A **preview drawer** that opens on card click. The drawer's "Use this recipe" CTA fires `onSelect(listing)` and (when `selectCapability` is supplied) dispatches the capability with `{ address }` via the host-supplied `dispatcher` — same dispatcher contract as `<DropZone>` / `<SelectionActionBar>`.

Wiring the real vault client is a one-line swap:

```ts
import { VaultMarketplaceClient } from '@atelier/vault-client';

const client = new VaultMarketplaceClient({
  vaultUrl: 'https://vault.example',
  trustedKeys,
});
```

Loading + empty states use the existing baseline primitives (`<Skeleton shape="card" count={6}>` while the first list call is in flight, `<EmptyState>` when the client returns zero matches), so the surface inherits the host's variant tokens automatically.

## What you DON'T do

- **Don't bypass signature verification.** If the signature doesn't verify, the bundle is suspect. Reject.
- **Don't auto-accept TOFU mismatches.** A key change is a serious event; surface it to the user.
- **Don't grant scopes the recipe doesn't ask for.** The recipe's `capability_grants` is the canonical list. Anything extra is host overreach.
