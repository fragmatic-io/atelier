This page walks an author through publishing a marketplace bundle end-to-end. The CLI surface is roadmap; today the flow is direct against the vault server.

## What you're publishing

A `SignedBundle`:

```json
{
  "address": {
    "scheme": "atelier",
    "author": "acme",
    "persona": "email-triage",
    "version": "1.0.0"
  },
  "payload": {
    "recipe": {
      /* RecipeSchema-shaped */
    },
    "skills": [
      { "name": "email-triage", "version": "1.0.0", "markdown": "..." },
      { "name": "task-extraction", "version": "1.0.0", "markdown": "..." }
    ],
    "brand_kit": {
      /* optional */
    }
  },
  "timestamp": "2026-05-02T12:00:00.000Z",
  "signature": "...",
  "public_key": "...",
  "key_id": "..."
}
```

## The walkthrough

<Steps>

1. **Author your recipe + skills + brand kit.**

   ```bash
   pnpm atelier init my-bundle
   cd my-bundle
   # edit recipes/founder-inbox.json + skills/*.skill.md
   ```

2. **Generate a signing key (one-time per author).**

   ```bash
   node -e "
     const crypto = require('crypto');
     const { publicKey, privateKey } = crypto.generateKeyPairSync('ed25519');
     require('fs').writeFileSync('~/.atelier/keys/acme.private.pem', privateKey.export({ format: 'pem', type: 'pkcs8' }));
     require('fs').writeFileSync('~/.atelier/keys/acme.public.pem', publicKey.export({ format: 'pem', type: 'spki' }));
   "
   chmod 600 ~/.atelier/keys/acme.private.pem
   ```

   The `atelier marketplace keygen` subcommand will ship; until then this one-liner does it.

3. **Build the bundle payload.**

   ```ts
   // build-bundle.ts
   import { canonicalJsonStringify } from '@atelier/schemas';
   import * as fs from 'node:fs';
   import * as crypto from 'node:crypto';

   const recipe = JSON.parse(fs.readFileSync('recipes/founder-inbox.json', 'utf-8'));
   const skills = fs.readdirSync('skills').map((file) => {
     const markdown = fs.readFileSync(`skills/${file}`, 'utf-8');
     const name = file.replace('.skill.md', '');
     return { name, version: '1.0.0', markdown };
   });

   const address = {
     scheme: 'atelier' as const,
     author: 'acme',
     persona: 'founder-inbox',
     version: '1.0.0',
   };

   const payload = { recipe, skills };
   const timestamp = new Date().toISOString();

   const canonical = canonicalJsonStringify({ address, payload, timestamp });

   const privateKey = crypto.createPrivateKey({
     key: fs.readFileSync(process.env.HOME + '/.atelier/keys/acme.private.pem'),
     format: 'pem',
   });
   const publicKey = crypto.createPublicKey(privateKey).export({ format: 'der', type: 'spki' });
   const publicKeyB64 = publicKey.toString('base64');
   const signature = crypto.sign(null, Buffer.from(canonical), privateKey).toString('base64');
   const key_id = crypto.createHash('sha256').update(publicKey).digest('hex').slice(0, 16);

   const bundle = {
     address,
     payload,
     timestamp,
     signature,
     public_key: publicKeyB64,
     key_id,
   };

   fs.writeFileSync('bundle.json', JSON.stringify(bundle, null, 2));
   ```

4. **Publish to the vault.**

   The CLI is the recommended path (V-6.f shipped):

   ```bash
   pnpm atelier marketplace publish bundle.json \
     --author acme \
     --key ~/.atelier/keys/acme.private.pem \
     --vault-url http://localhost:4001
   ```

   Under the hood the CLI loads the PEM, signs `{address, payload, timestamp}`
   with ed25519, and POSTs the resulting `SignedBundle` to
   `POST /marketplace/persona`. On success, the canonical address is
   printed to stdout and exit code 0 is returned.

   The same flow is available programmatically via
   `publishPersona(client, bundle, author)` from `@atelier/vault-client`.

   For curl users:

   ```bash
   # Build the SignedBundle yourself (see step 3) then POST it raw:
   curl -X POST http://localhost:4001/marketplace/persona \
     -H 'content-type: application/json' \
     -d @signed-bundle.json
   ```

   On success: `201 Created` with `{ address, key_id }`.

   On failure:
   - `400 { error: 'malformed bundle', issues: [...] }` — schema mismatch.
   - `401 { error: 'signature verification failed', reason: '...' }` — the
     signature didn't verify against the AUTHOR'S registered key in the
     server's `KeyDirectory`. (Unknown author handles also 401 here.)
   - `409 { error: 'duplicate', address }` — `(author, persona, version)`
     is already published. Bump the version to publish again.

5. **Verify the publish.**

   ```bash
   curl http://localhost:4001/marketplace/persona/acme/founder-inbox@1.0.0
   ```

   You should see the bundle round-tripped verbatim. The vault stores what you sent; it never re-signs.

   To grab the highest semver for an `(author, persona)`:

   ```bash
   curl http://localhost:4001/marketplace/persona/acme/founder-inbox/latest
   ```

   Returns `{ address, bundle }` — the canonical address of the latest
   version + the full `SignedBundle` so the client can re-verify.

</Steps>

## What the vault checks

When a bundle hits `POST /marketplace/persona`:

1. **Schema parse.** The body must match `SignedBundleSchema`. Malformed → 400.
2. **Author registration.** `bundle.address.author` must resolve to a
   public key in the server's `KeyDirectory`. Unknown → 401.
3. **Signature verification.** The signature must verify against the
   AUTHOR'S registered key (not the bundle's embedded `public_key`,
   which is a verifier-convenience copy) over the canonical JSON of
   `{ address, payload, timestamp }`. Bad signature → 401.
4. **Key id check.** `bundle.key_id` must match the registered key's
   fingerprint. Mismatch → 401.
5. **Address validation.** Author / persona / version must match the canonical regex / semver shape. Malformed → 400.
6. **Duplicate check.** `(author, persona, version)` must not already
   exist in the store. Duplicate → 409.
7. **Store.** If everything passes, the bundle is persisted verbatim
   and indexed by `(author, persona, version)`.

The vault never re-signs. It's a durable storage + re-serving surface, not a re-attestation authority. Per-version content is immutable by construction — the server returns 409 on a duplicate; bumping the version is the only way to publish again.

## Authoring workflow tips

- **Bump `version` for every change.** Per-version immutability is a follow-up; until then the recommended discipline is to bump for any publish.
- **Sign canonical JSON, not pretty JSON.** The encoder sorts keys at every depth; `JSON.stringify(value, null, 2)` does NOT produce canonical output.
- **Test verification before publish.** Run `verifySignature(canonical, signature, publicKey)` locally; if that fails, the publish will fail too.
- **Don't ship private keys.** The bundle carries the public key; the private key never leaves your environment.
- **Document the bundle.** Recipes are dense; consumers want to know what scopes they're granting and what skills are included before they install. A `README.md` alongside each bundle helps.

## Distribution beyond a single vault

Today, a publish targets one vault. Multi-vault distribution (mirroring across hosts) is roadmap. The signed bundle's authenticity travels with the bytes — any Atelier-compatible vault can serve it once it has the bytes — but discovery / federation is V-6+.

## Republishing semantics

| Scenario                                                             | Result                                                                                      |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Publish to existing `<author>/<persona>@<version>` (any key)         | `409 duplicate`. Bump the version.                                                          |
| Publish with a key not in the server's `KeyDirectory` for `<author>` | `401 signature verification failed`.                                                        |
| Publish a new version                                                | New bundle; old version still fetchable. `latest` route now returns the new highest semver. |

Per-version content is immutable: the new `POST /marketplace/persona` endpoint returns 409 rather than overwriting. (The legacy `POST /vault/marketplace/publish` endpoint is preserved with its overwrite semantics for back-compat with the v0 demos.)

## Review & curation (V-6.d)

When a bundle hits `POST /marketplace/persona`, the server **auto-creates a
`pending` `ReviewRecord`** alongside the stored bundle. Direct-address fetches
(`GET /marketplace/persona/<a>/<p>@<v>`) keep working — useful for authors
previewing their own work — but the **default browse index**
(`GET /marketplace/index`) only surfaces records whose state is `approved`.

### Review states

| State      | In default index? | Meaning                                                                                |
| ---------- | ----------------- | -------------------------------------------------------------------------------------- |
| `pending`  | no                | Auto-applied on first publish. Awaiting maintainer review.                             |
| `approved` | yes               | Curated and visible in the default browse index.                                       |
| `rejected` | no                | Refused by a maintainer. Direct fetch still resolves (so the author can see).          |
| `flagged`  | no                | Under active review (e.g. user report). Visible to maintainers via `?include=flagged`. |

### Submit a review (maintainer)

Maintainer keys are registered in the server's `ReviewerKeyDirectory` (a separate
directory from the publish-side `KeyDirectory` — a maintainer key proves "I am an
authorized reviewer", not "I am this author"). The CLI surface signs the review
envelope with the maintainer's PKCS#8 ed25519 PEM and POSTs it.

```bash
pnpm atelier marketplace review atelier://acme/founder-inbox@1.0.0 \
  --state approved \
  --reviewer maint-a \
  --key ~/.atelier/keys/maint-a.private.pem \
  --notes "LGTM after security pass."
```

On success the persisted state + address are printed to stdout. Failures:

- `401` — reviewer not registered, or signature verification failed.
- `404` — no bundle exists at that address (bundle must be published first).
- `400` — schema mismatch in the request body.

### Programmatic API

```ts
import { submitReview, fetchReview, listMarketplace } from '@atelier/vault-client';

await submitReview(client, 'atelier://acme/founder-inbox@1.0.0', {
  state: 'approved',
  reviewerId: 'maint-a',
  privateKey: maintainerPrivateKeyBytes,
  notes: 'LGTM after security pass.',
});

const record = await fetchReview(client, 'atelier://acme/founder-inbox@1.0.0');
console.log(record?.state);

// Default: approved-only.
const approved = await listMarketplace(client);

// Maintainer escape hatch — see all curated states.
const queue = await listMarketplace(client, {
  include: ['pending', 'flagged', 'rejected'],
});
```

### Index query parameters

`GET /marketplace/index` accepts the same filter shape as the V-6.c
`<MarketplaceBrowser>` component:

| Param        | Effect                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------- |
| `author`     | Limit to a single author handle.                                                                        |
| `domain`     | Limit by `payload.domain`.                                                                              |
| `brandKitId` | Limit by `payload.brand_kit_id` / `payload.brandKitId` (either form).                                   |
| `search`     | Case-insensitive substring across persona / description / authorDisplayName.                            |
| `limit`      | Clamp to first n results.                                                                               |
| `offset`     | Skip first n results.                                                                                   |
| `include`    | Comma-separated escape hatch. Default: `approved`. Maintainers pass `pending,flagged` to see the queue. |
