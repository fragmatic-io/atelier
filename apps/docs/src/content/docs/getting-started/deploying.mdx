This page covers the production deploy paths Atelier supports today. The framework is deliberately host-neutral — the `@atelier/runtime` package has no opinions about where it runs — but the demo wiring is Next.js 15, so the worked examples follow that.

## What you're deploying

A typical Atelier app has four deployable surfaces:

1. **The host.** Next.js / Vite / Express / your Node server. Owns the routes, the API endpoints (`/api/cir/compile`, `/api/cir/audit/stream`, `/api/triggers/publish`), and the bundled React adapter (`@atelier/react`).
2. **The vault.** `@atelier/vault-server` — the user-owned intent store. Can be the reference Node server (`atelier vault dev`), self-hosted on a different domain, or a third-party Atelier-compatible vault.
3. **The compiler service.** Where `@atelier/compiler` runs. Today the demo runs it inline in the Next.js process; production deploys typically split it onto a dedicated worker pool because LLM calls are slow and the host should stay snappy.
4. **The capability + skill + component artifact registries.** Static, immutable per-version files (signed). Often served from the host itself (`/.well-known/cir.json`), or from an edge CDN if you have many capabilities.

Each of these can scale independently.

## Single-process deploy (smallest)

For an MVP, ship everything in one Node process:

```text
┌────────────────────────────────────────────────┐
│  one Node process                              │
│  - Next.js host                                │
│  - @atelier/compiler (in-process)              │
│  - @atelier/vault-server (in-process or peer)  │
│  - MemoryManifestStore                         │
│  - InMemoryTriggerBus                          │
└────────────────────────────────────────────────┘
```

Boot via `pnpm build && pnpm start`. Deploy to Fly.io / Railway / Render / Vercel-Node.

This is the demo's wiring out of the box. Suitable up to ~1k DAU before the LLM calls start to dominate.

## Split compile-worker deploy (recommended for production)

Once the host's request rate justifies it, split the compile loop onto a worker pool:

```text
┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
│  Next.js     │────▶│  Compile worker  │────▶│  LLM provider │
│  host        │     │  (@atelier/...)  │     │  (Gemini/etc) │
└──────────────┘     └──────────────────┘     └──────────────┘
       │                     │
       └─────▶ ManifestStore ◀┘
              (Redis or KV)
```

The host calls the worker over HTTP; the worker hits the LLM, and the host-side resolver validates the returned manifest against `BASELINE_POLICIES` before storing it in `RedisManifestStore`. The host reads from the same store on subsequent requests.

Concretely:

```ts
// lib/cir-server.ts (host side)
import {
  createBaselineManifestValidator,
  ServerManifestResolver,
  RedisManifestStore,
} from '@atelier/compiler';

const resolver = new ServerManifestResolver({
  store: new RedisManifestStore({ url: process.env.REDIS_URL }),
  compileEndpoint: process.env.COMPILE_WORKER_URL, // e.g. https://compile.example/compile
  validate: createBaselineManifestValidator({
    grantedFields: (input) => loadGrantedFields(input.user_id),
  }),
});
```

The worker process imports `GeminiCompiler` directly and returns compiler output. `ServerManifestResolver` is the central policy gate before cache write.

## Trigger bus for multi-region

The default `InMemoryTriggerBus` is single-process. For multi-process / multi-region deploys, switch to a distributed bus. Track S-4 in the roadmap; the seam is the `TriggerBus` interface.

```ts
import { RedisTriggerBus } from '@atelier/runtime'; // when S-4 lands

const bus = new RedisTriggerBus({ url: process.env.REDIS_URL });
```

In the meantime, a thin `RedisTriggerBus` is straightforward to write against the published interface.

## Vault deploy

The reference `@atelier/vault-server` is a Node `http` server with JSON-file storage. For production:

- **Self-host** on a sibling subdomain (`vault.your-app.com`). Run behind a reverse proxy with TLS.
- **Persist with SQLite** when V-1's SQLite adapter lands (gated on Node 24's stable `node:sqlite`). Until then JSON-file storage is fine for low-write-volume use cases.
- **Multi-key JWKS rotation.** The reference server today emits a single key; multi-key rotation is on the roadmap.

The vault speaks the protocol documented in [`docs/vault-protocol.md`](https://github.com/fragmatic-io/atelier/blob/main/docs/vault-protocol.md). Any third-party vault implementing it is interchangeable.

## Static artifacts

`capabilities/`, `skills/`, `components/registry.json`, `policies/`, `recipes/` are static files. Either:

- Serve them from the host directly under `/capabilities/<id>@<version>` etc. (the simple path).
- Push them to a CDN with infinite TTL per version. Bump the version when contents change; the cache key includes the version so old manifests stay valid until a trigger forces a recompile.

The `.well-known/cir.json` discovery file points at all four.

## Observability in production

Atelier's audit pipeline is the source of truth. Pipe `StreamingAuditSink` to your logging system:

```ts
import { CompositeAuditSink, StreamingAuditSink } from '@atelier/runtime';

const audit = new CompositeAuditSink([
  new StreamingAuditSink({ writer: yourSseHub }),
  new HttpForwardingSink({ url: 'https://logs.example/atelier' }),
]);
```

Every compile, every action dispatch, every policy validation, every trigger fires through this pipeline. See [Operations → Observability](/operations/observability/).

## Cost control in production

`BudgetMeteredCompiler` from `@atelier/compiler` wraps any compiler and enforces a per-user / per-app token budget. Throws `BudgetExceededError` when crossed; the host typically maps this to a `429` plus a "you've hit your daily personalisation budget" UX surface.

```ts
import { BudgetMeteredCompiler, mergeCompileBudgets } from '@atelier/compiler';

const compiler = new BudgetMeteredCompiler(
  new GeminiCompiler({ apiKey: process.env.GEMINI_API_KEY! }),
  { budget: { tokens: 50_000, window_ms: 86_400_000 }, counter: yourBudgetCounter },
);
```

See [Compiler → Budget](/compiler/budget/) and [Operations → Cost control](/operations/cost-control/).

## Deploying the docs site itself

This very site lives in `apps/docs/`. It's a Starlight app that builds to a static `dist/`. The repo's `.github/workflows/site-deploy.yml` builds on push to `main`, uploads the artifact, and `actions/deploy-pages@v4` publishes it under `/atelier/` on `fragmatic-io.github.io`.

After the P3 site merge (2026-05-04), the marketing surface (homepage + `/start/` + `/architecture/` + `/demos/`) lives in this same Starlight site as splash / docs pages — there is no longer a separate `apps/marketing` package.

<Aside type="caution">
  GitHub Pages allows one source per repository. If you deploy multiple Astro apps to one Pages
  site, the workflows must merge artifacts before upload (see `.github/workflows/site-deploy.yml`) —
  you can't ship two independent `actions/deploy-pages@v4` jobs.
</Aside>
