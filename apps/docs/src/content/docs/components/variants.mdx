Most baseline components ship two declarative axes: **variant** (semantic intent) and **size** (visual scale). The compiler picks values; the renderer maps them to CSS-variable consumption from the brand kit.

## The axes

| Axis      | Typical values                                                       |
| --------- | -------------------------------------------------------------------- |
| `variant` | `primary`, `secondary`, `ghost`, `destructive`, `success`, `warning` |
| `size`    | `xs`, `sm`, `md`, `lg`, `xl`                                         |

Not every component supports every value. The contract enforces the legal set.

## Example: `<Button>`

```tsx
<Button variant="primary" size="md">Save</Button>
<Button variant="destructive" size="sm">Archive</Button>
<Button variant="ghost" size="md" icon="archive">Archive</Button>
```

The compiler emits manifest nodes with `props.variant` and `props.size`; the renderer maps them through the brand kit's elevation + color + density tokens.

## Where the values come from

The brand kit's `color.semantic` and `density.*` tokens drive what `variant` and `size` actually look like. So the same manifest, rendered against two different brand kits, produces visually different but structurally identical UIs.

```text
brand_kits/aurora.json     →  variant=primary  →  #6e56cf
brand_kits/octant-dark.json →  variant=primary  →  #1f6feb
```

This is the marketplace promise: **manifest is the contract; brand is the styling**. Recipes don't pick colors; they pick semantic variants.

| Wave  | Components covered                                                                      |

## The variants registry

```ts
// packages/components/src/_variants.ts (excerpt)
export const BUTTON_VARIANTS = {
  primary: 'bg-[--cir-color-primary] text-white hover:bg-[--cir-color-primary-hover] dark:...',
  secondary: 'bg-[--cir-color-neutral-2] text-[--cir-color-fg] dark:...',
  ghost: 'bg-transparent text-[--cir-color-fg] hover:bg-[--cir-color-neutral-1] dark:...',
  destructive: 'bg-[--cir-color-danger] text-white hover:opacity-90 dark:...',
};

export const BUTTON_SIZES = {
  xs: 'h-7 px-2 text-xs',
  sm: 'h-8 px-3 text-sm',
  md: 'h-10 px-4 text-sm',
  lg: 'h-11 px-5 text-base',
  xl: 'h-14 px-6 text-lg',
};
```

Every entry in `_variants.ts` ships paired light + `dark:` Tailwind utilities. The Vis-2 regression gate at `test/_variants-dark.test.ts` enforces this.

## Variant validation

The component contract declares the legal variant set:

```ts
const ButtonContract = {
  props: z.object({
    variant: z.enum(['primary', 'secondary', 'ghost', 'destructive']),
    size: z.enum(['xs', 'sm', 'md', 'lg', 'xl']).default('md'),
    // ...
  }),
};
```

A manifest with `variant: 'tertiary'` is rejected at validate time. The compiler can't pick something illegal; the renderer never sees a malformed prop.

## Custom variants

Hosts can layer their own semantic variants. The brand kit declares them; the contract accepts them; `_variants.ts` maps them.

```ts
// brand_kits/yours.json
{
  "color": {
    "semantic": { "success": "...", "warning": "...", "danger": "...", "highlight": "#ffd60a" }
  }
}

// Extending the contract:
ButtonContract.props.variant = z.enum(['primary', 'secondary', 'ghost', 'destructive', 'highlight']);
```

The compiler reads the brand kit and surfaces the new variant as a legal value via `inspectComponent`. The renderer reads the variants registry and renders accordingly.

## Density coupling

Variants don't drive density; density flows from `intent.global_preferences.density` independently. So `<Button variant="primary" size="md">` rendered under `compact` density has tighter padding than the same Button under `spacious` density. The two axes compose.

## The "tone" pattern

Some components have a third axis — `tone` — for shapes that semantically describe state rather than emphasis. `<Toast tone="info">` vs `<Toast tone="warning">` vs `<Toast tone="success">`. This isn't universal across the catalog; check the per-component contract.
