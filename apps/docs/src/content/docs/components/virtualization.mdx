Wave S-2 shipped virtualization as a first-class concern. `<VirtualList>` and `<VirtualTable>` mirror the `<List>` and `<Table>` surfaces but back onto `@tanstack/react-virtual` and emit `onFetchMore` / `onFetchPrev` at scroll edges.

## When the compiler picks them

The `composes_hierarchy_for_long_lists` policy nudges the compiler toward the virtual variant when a bound capability declares `expected_count > 500` (default `VIRTUAL_THRESHOLD`):

```json
// capabilities/repo.list.json
{
  "id": "repo.list",
  "kind": "data",
  "version": "1.0.0",
  "input": { "filter": "...", "cursor": "..." },
  "output": { "items": "...", "next_cursor": "..." },
  "pagination": "cursor",
  "expected_count": 5000
}
```

Compiler sees `expected_count: 5000`, swaps `<List>` for `<VirtualList>`. No author intervention.

## The `<VirtualList>` shape

```tsx
<VirtualList
  data={{ source: 'repo.list', filter: 'user = vid', sort: 'updated_at desc' }}
  itemHeight={56}
  overscan={8}
  onFetchMore={(cursor) => /* runtime wires this through DataResolver.paginate */}
/>
```

Props mirror `<List>` plus virtualization-specific knobs (`itemHeight`, `overscan`, `onFetchMore`, `onFetchPrev`). The runtime wires the fetch-more / fetch-prev callbacks; the host doesn't author these.

## Cursor pagination

`@atelier/data-resolvers` ships `paginate()` and a `CursorPaginatedResult` envelope on `DataBinding`:

```ts
import { paginate } from '@atelier/data-resolvers';

const fetchPage = async (cursor: string | null) => {
  const result = await fetch(`/api/repos?cursor=${cursor ?? ''}`);
  const json = await result.json();
  return {
    items: json.items,
    next_cursor: json.next_cursor,
    prev_cursor: json.prev_cursor,
  };
};

const resolver = new InMemoryDataResolver({
  'repo.list': paginate(fetchPage),
});
```

The resolver yields paged results; `<VirtualList>` consumes them via the `useDataBinding` hook in `@atelier/react`.

## Backwards compatibility

Bindings without `pagination` declared default to `'none'`. Resolvers returning plain arrays continue to work. The virtualization track is fully additive — no manifest needs updating to keep working post-S-2.

```ts
// works pre- and post-S-2
const flatList = await resolver.fetch({ source: 'thread.list', filter: '...' });
//   flatList === Array<Thread>  (no pagination)

// new in S-2
const paged = await resolver.fetchPage({ source: 'repo.list', filter: '...', cursor: null });
//   paged === { items: Repo[], next_cursor: '...', prev_cursor: null }
```

## The `<VirtualTable>` shape

```tsx
<VirtualTable
  data={{ source: 'repo.list', filter: '...' }}
  columns={[
    { id: 'name', label: 'Repository', cell: 'string' },
    { id: 'stars', label: 'Stars', cell: 'number', tnum: true },
    { id: 'updated_at', label: 'Updated', cell: 'date' },
  ]}
  rowHeight={48}
  overscan={6}
/>
```

Same composition rules apply; the renderer just swaps the row implementation for the virtualized variant. Density-aware (consumes `data-cir-density`).

## Density integration

Virtual variants honour density just like their non-virtual counterparts:

```tsx
<VirtualList
  data={...}
  itemHeight={resolveDensity(intent, route) === 'compact' ? 40 : 56}
/>
```

In practice the height is resolved per-render from the brand kit; manifest authors don't compute it.

## Performance characteristics

- **Cold render:** ~10ms for any list size (only visible rows mount).
- **Scroll:** 60fps to 200fps depending on row complexity.
- **Memory:** O(viewport rows + overscan), not O(total rows).
- **Pagination fetch:** triggered ~200px before scroll edge; SWR cache absorbs round-trip jitter.

## When NOT to virtualize

- Lists with `< 100` items where fetching all-at-once is cheap. `<List>` and `<Table>` are simpler and keyboard-navigation works without virtualization quirks.
- Lists where every row's height varies wildly. `@tanstack/react-virtual` supports dynamic measurement, but the simpler `<List>` is a better fit for unpredictable row heights below the threshold.
- Lists in modals / drawers where the viewport itself is bounded and small. The savings don't justify the overhead.
