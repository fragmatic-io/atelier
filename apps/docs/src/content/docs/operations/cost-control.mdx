Tokens are the operational cost of the system. The architecture is engineered around minimizing them. Cache hit rate is the single most important number; everything else is downstream.

## Token economics

Per-call costs (rough, mid-2026 pricing):

| Operation                  | Tokens   | Cost (Sonnet) | Cost (Opus) |
| -------------------------- | -------- | ------------- | ----------- |
| Trigger classification     | 200-500  | $0.001        | $0.005      |
| Skill discovery            | 1k-3k    | $0.005        | $0.025      |
| Diff recompile             | 3k-10k   | $0.02         | $0.10       |
| Cold compile (small route) | 8k-20k   | $0.05         | $0.25       |
| Cold compile (complex app) | 20k-60k  | $0.15         | $0.75       |
| Cross-app workflow compile | 50k-150k | $0.40         | $2.00       |

## Per-user economics

A typical user:

| User type                         | Compiles/month | Avg tokens | Cost/month    |
| --------------------------------- | -------------- | ---------- | ------------- |
| Light (consumer)                  | 2-5            | 10k        | $0.05 - $0.25 |
| Medium (prosumer)                 | 10-20          | 15k        | $0.30 - $1.50 |
| Heavy (power user)                | 30-60          | 25k        | $1.50 - $7.50 |
| Tinkerer (constantly customizing) | 100+           | 20k        | $5 - $30      |

This assumes proper caching. Without caching — recompile every render — costs are 100-1000x higher and the system is economically unviable.

## Optimization levers (in order of impact)

### 1. Cache aggressively

A 95% cache hit rate vs 70% is a 6x cost difference. Every architectural decision serves the cache hit rate.

The cache cascade: T5 (browser memory) → T4 (browser IndexedDB) → T3 (server `ManifestStore`) → compile. Most renders never touch T3.

### 2. Diff mode over full recompile

Most triggers change a small piece of context. The compiler's prompt should include the prior manifest and ask only for the diff. **70-90% token savings.** `ValidationFeedbackCompiler` already runs in diff-mode style for retries.

### 3. Tiered model routing

- **Trigger classification:** tiny model (Gemini Flash, Haiku). Decides "does this trigger require recompile?" — 80% of triggers don't.
- **Diff recompile:** medium model.
- **Cold compile:** large model.
- **Cross-app workflow:** large model with extended context.

Most companies will use 3-5 model tiers depending on workload.

### 4. Skill density

A well-written skill replaces hundreds of tokens of compiler reasoning. Investing in good skills is the highest-leverage token optimization. **Ship skills as carefully as you ship APIs.** See [Concepts → Skill](/concepts/skill/).

### 5. Component vocabulary

A rich, well-named component catalog means the compiler describes UI in component names, not in raw structure. "Use a Queue grouped by sender" is 10 tokens; describing the same UI structurally is 500.

The marketplace pivot's promotions (`<Queue>`, `<Logo>`, data-aware `<Grid>` / `<Card>` / `<Gallery>`) directly serve this.

### 6. Pre-compiled recipes

For common personas (founder, student, sales), ship a default recipe per persona. New users start with a pre-warm; the system never compiles from cold for them.

### 7. Org-level cache

In B2B, multiple users in the same org often want the same lenses. Cache at the org level for shared manifests, personalize via thin diff overlays.

### 8. Edge inference for small triggers

Trigger classification can run on small open models at the edge. Only escalate to large models when the classifier is uncertain.

### 9. Speculative compilation

When the user does X, the system predicts they'll likely want Y next and pre-compiles in the background. Wasted compute is cheap compared to user-perceived latency.

### 10. Token budget per user, exposed

Power users who customise constantly should see their token usage. Most won't care. Ones who do can self-throttle or upgrade. This is far better than silently capping. See [Compiler → Budget enforcement](/compiler/budget/).

## Budget enforcement

`BudgetMeteredCompiler` from `@atelier/compiler` enforces a per-user / per-app token budget:

```ts
import { BudgetMeteredCompiler, RedisBudgetCounter } from '@atelier/compiler';

const compiler = new BudgetMeteredCompiler(innerCompiler, {
  budget: { tokens: 50_000, window_ms: 86_400_000 }, // 50k tokens / 24h
  counter: new RedisBudgetCounter({ url: process.env.REDIS_URL! }),
  keyOf: (input) => `user:${input.user_id}`,
});
```

Layered budgets (per-user + per-org):

```ts
const userBudget = new BudgetMeteredCompiler(inner, {
  budget: { tokens: 50_000, window_ms: 86_400_000 },
  counter,
  keyOf: (input) => `user:${input.user_id}`,
});

const orgBudget = new BudgetMeteredCompiler(userBudget, {
  budget: { tokens: 5_000_000, window_ms: 86_400_000 },
  counter,
  keyOf: (input) => `org:${input.org_id}`,
});
```

`BudgetExceededError` cascades through `CompositeCompiler` → `GenericFallbackCompiler`. The user sees the fallback manifest; the host's bill stays bounded.

## Pricing implications

The asymmetry between cache-hit users and customizers is real. A pricing model that reflects it:

- **Free tier:** pre-compiled recipes only, no custom recompilation.
- **Pro tier:** monthly token budget covering typical customization.
- **Power tier:** usage-based pricing for heavy customizers.
- **Enterprise:** org-level cache + token pool + dedicated compute.

This mirrors how cloud infra is sold. Users who consume more pay more, but the median user pays nothing extra because their cache hit rate is near 100%.

## Cost dashboards

The framework's [Cost dashboard](/operations/cost-dashboard/) auto-aggregates the trailing window of marketplace LLM eval runs (`marketplace-eval-llm.yml`, 04:30 UTC daily) and surfaces:

- per-persona avg + p95 USD cost,
- trend (up / down / stable across the window),
- top 5 most-expensive personas,
- 7-day and 30-day rolling spend.

The page is regenerated on every nightly run and committed back to main, so the rendered MDX always tracks the latest eval-reports.

For host-side dashboards, aggregate the audit log:

```sql
-- Daily compile cost per user
SELECT
  user_id,
  DATE(timestamp) AS date,
  SUM(token_cost) AS tokens,
  SUM(token_cost) * 0.000005 AS cost_usd
FROM audit_events
WHERE type = 'manifest.compiled'
GROUP BY 1, 2
ORDER BY 3 DESC;

-- Cache hit rate per route
SELECT
  route,
  COUNT(*) FILTER (WHERE type = 'manifest.cache_hit') / NULLIF(COUNT(*), 0) AS hit_rate
FROM audit_events
WHERE type IN ('manifest.cache_hit', 'manifest.cache_miss')
GROUP BY route;
```

`<CompileBadge>` in the demo surfaces the user-facing version. `<DebugPanel>` shows the developer-facing aggregate.

## When to escalate

- **Cache hit rate &lt;70%:** something is invalidating too aggressively. Check trigger frequency.
- **Compile p99 >5s:** prompt is too big or model is too slow. Profile the prompt.
- **Token spend exceeding the budget for >5% of users:** raise the budget or invest in skill density.
