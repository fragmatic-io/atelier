A **capability** is a typed action or data resource the app exposes to the compiler. It's the public, signed, versioned interface between "what the system can do" and "the LLM that has to decide whether to do it".

Capabilities are described in JSON files (one per file) that match `CapabilitySchema` in `@atelier/schemas`.

## Anatomy

```json
// capabilities/thread.archive.json
{
  "id": "thread.archive",
  "kind": "action",
  "version": "2.1.0",
  "input": {
    "thread_id": { "type": "string" }
  },
  "output": {
    "archived_at": { "type": "string", "format": "date-time" }
  },
  "side_effects": ["mutates:thread_state"],
  "permissions": ["thread:write"],
  "confirmation": "modal",
  "rate_limit": "100/min/user",
  "reversible": true,
  "rollback": "thread.unarchive",
  "salience_level": "medium",
  "low_stakes": true
}
```

## The fields

| Field              | Purpose                                                                                                        |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| `id`               | Stable identifier. Used everywhere — recipes, manifests, audit logs.                                           |
| `kind`             | `"action"` (mutating) or `"data"` (read-only).                                                                 |
| `version`          | Semver. Cache keys include the version; bumping it invalidates manifests.                                      |
| `input` / `output` | JSON-Schema-shaped descriptors. The compiler reads these to know what data to bind.                            |
| `side_effects`     | What happens beyond the response. Drives the policy engine (`destructive` triggers `confirmation_required`).   |
| `permissions`      | Auth scopes the user must hold.                                                                                |
| `confirmation`     | `"none"` / `"modal"` / `"verbal_required"`. The dispatcher renders the matching surface before firing.         |
| `rate_limit`       | `100/min/user` parser. The dispatcher and the optimistic-UI hook both read this.                               |
| `reversible`       | Boolean. If `true`, the runtime can wire `withUndo()` middleware automatically.                                |
| `rollback`         | The capability id that undoes this one. Required when `reversible: true`.                                      |
| `salience_level`   | `"low"` / `"medium"` / `"high"`. Drives `<Queue>` emphasis, hierarchy, and the salience-aware-rendering skill. |
| `low_stakes`       | Combined with `reversible: true`, makes `useOptimisticAction` auto-wire (Wave 7 P-9 / Int-4).                  |
| `expected_count`   | Optional. When `> 500`, the policy engine nudges the compiler toward `<VirtualList>` / `<VirtualTable>` (S-2). |

## Data capabilities

Read-only capabilities use `kind: "data"` and declare a `pagination` strategy:

```json
// capabilities/thread.list.json
{
  "id": "thread.list",
  "kind": "data",
  "version": "1.0.0",
  "input": {
    "filter": { "type": "string", "default": "" },
    "sort": { "type": "string", "default": "received_at desc" },
    "cursor": { "type": "string", "nullable": true }
  },
  "output": {
    "items": { "type": "array" },
    "next_cursor": { "type": "string", "nullable": true }
  },
  "permissions": ["thread:read"],
  "pagination": "cursor",
  "expected_count": 5000
}
```

The `expected_count: 5000` triggers the `composes_hierarchy_for_long_lists` policy to suggest `<VirtualList>` over `<List>` on the next compile. See [virtualization](/components/virtualization/).

## Why capabilities are first-class

Three reasons:

1. **The LLM has to know what's available.** A capability registry is the compiler's vocabulary. No registry → the LLM either invents capabilities (broken UI) or refuses to compile.
2. **The runtime has to validate dispatch.** When the user clicks "Archive", the dispatcher confirms the capability exists, the user has the permission, the rate limit isn't blown, and the side effects are surfaced. All of that lives in the capability declaration.
3. **The cache has to invalidate correctly.** The cache key includes the capability registry version. Bumping `thread.archive` from `2.1.0` to `2.2.0` invalidates every manifest that depends on it.

## Versioning

Capabilities are versioned independently. The cache key is:

```text
manifest:{user_id}:{app_id}:{route}
  :cap_{capability_registry_version}
  :cmp_{component_catalog_version}
  :skl_{skill_set_hash}
  :int_{intent_profile_version}
  :pol_{policy_set_version}
```

Old manifests stay valid for users still on old artifact versions; new manifests are computed only for combinations that actually need them. See [Caching](/operations/performance/#caching-tiers).

## Validating a capability file

```bash
pnpm exec atelier-schemas validate-data --strict
```

The `--strict` flag fails on `_review` envelope drafts (placeholder capabilities still under review). CI enforces strict in `validate-data.yml`.

## Custom field extensions

`CapabilitySchema` accepts unknown top-level keys with a deliberate `passthrough` hatch — apps can layer their own metadata (`team_id`, `cost_center`, etc.) without forking the schema. The runtime ignores anything it doesn't recognise.
