A **recipe** is the file humans author. A **manifest** is the file the LLM authors. The compiler is the bridge between them.

This is the single most important boundary in Atelier. Get it wrong and you end up with humans hand-tuning manifests (a smell — principle #6) or LLMs inventing capabilities (a bug — principle #2).

## The boundary

```text
HUMAN AUTHORED                       │ LLM AUTHORED
  recipes/founder.json               │   manifests/m_8f3a2b1c.json
  ETHOS.md                           │
                                     │
  capabilities/thread.archive.json   │   tree of <Stack> / <Queue> / <Card>
  skills/email-triage.skill.md       │   nodes with bound capability ids,
  components/registry.json           │   props chosen from the component
  policies/destructive-confirm.json  │   contract, actions wired to the
                                     │   declared action slots.
                                     │
  brand_kits/aurora.json             │
                                     │
                          ↓          ↓
                        compiler reads left,
                        emits right.
```

## What a recipe declares

```json
// recipes/founder.json
{
  "id": "recipes:founder",
  "version": "1.0.0",
  "persona": "founder",
  "description": "Investor + customer email triage with a bias toward action.",
  "intent_defaults": {
    "global_preferences": {
      "density": "compact",
      "modal_tolerance": "low",
      "automation_trust": "drafts_only"
    },
    "lenses": { "email": "founder_inbox" },
    "rules": [{ "scope": "*", "rule": "Never auto-send. Drafts only.", "locked": true }]
  },
  "capability_grants": [
    "thread.list",
    "thread.read",
    "thread.archive",
    "thread.unarchive",
    "task.create_from_thread",
    "task.list",
    "task.complete",
    "task.snooze"
  ],
  "candidate_skills": ["email-triage", "task-extraction", "decision-separation"],
  "policy_obligations": [
    "reversibility_surfaced",
    "no_destructive_actions_without_confirm",
    "data_scope_within_grant"
  ],
  "routes": [
    { "path": "/today", "title": "Today" },
    { "path": "/thread/[id]", "title": "Thread" }
  ]
}
```

Five sections:

- **Intent defaults** — what the user starts with before they personalise. The user's actual `IntentProfile` (in the vault) overrides these.
- **Capability grants** — which capabilities the recipe wants the user to consent to. Drives the vault consent screen.
- **Candidate skills** — the skills the compiler may compose from. Filters the skill vocabulary so the prompt stays small.
- **Policy obligations** — the policies the manifest MUST satisfy. The validator enforces these.
- **Routes** — the route surface the recipe covers.

## What a manifest is

A specific tree of bound nodes that the compiler emitted for `(recipe + intent + capabilities + components + brand_kit)`. See [Concepts → Manifest](/concepts/manifest/).

## Why two artifacts?

Three reasons:

1. **Reviewability.** A recipe is small (~50-200 lines) and human-readable. A manifest is mechanical output. Code review the recipe; the compiler reproduces the manifest.
2. **Compiler determinism is impossible.** The same recipe + intent + version of the LLM will produce slightly different manifests. The recipe is the stable artifact; the manifest is the cached result.
3. **Versioning surface.** Recipes can be signed, shared, and published to the marketplace (`atelier://acme/founder@1.0.0`). Manifests are user-keyed cache entries.

## Recipe → manifest example

Given `recipes/founder.json` above, plus a user's intent (`density: spacious`, no rule overrides), the compiler might emit:

```json
{
  "manifest_id": "m_a1b2c3",
  "compiled_from": { "recipe_id": "recipes:founder", "intent_profile_version": 7 },
  "routes": [
    {
      "path": "/today",
      "title": "Today",
      "layout": {
        "component": "Stack",
        "props": { "gap": "lg" },
        "children": [
          {
            "component": "Queue",
            "props": { "title": "Decisions", "density": "spacious" },
            "data": { "source": "thread.list", "filter": "requires_decision = true" },
            "actions": ["task.create_from_thread", "thread.archive"]
          },
          {
            "component": "Queue",
            "props": { "title": "Tasks", "density": "spacious", "group_by": "due_date" },
            "data": { "source": "task.list", "filter": "due_within = 7d AND status != done" },
            "actions": ["task.complete", "task.snooze"]
          }
        ]
      }
    }
  ],
  "policies_satisfied": [
    "reversibility_surfaced",
    "no_destructive_actions_without_confirm",
    "data_scope_within_grant"
  ]
}
```

The recipe is the same for every user. The manifest reflects this user's density preference (`spacious` instead of the default `compact`).

## Authoring rules of thumb

- **Keep capability grants tight.** The recipe should only request capabilities the persona actually needs.
- **Pre-load candidate skills.** The compiler can find skills via `findSkill` (when C-5 lands), but for now, listing them in the recipe is the canonical surface.
- **List policy obligations explicitly.** Don't rely on the validator's defaults — name what you want enforced.
- **Don't pre-write manifest fragments.** Recipes are intent + grants + obligations, not layout. If you find yourself encoding "use a `<Queue>` with `density=compact`" in the recipe, you're authoring a manifest. Stop.

## Marketplace recipes

The marketplace's primary unit of distribution is a recipe bundle. `atelier://acme/email-triage@1.0.0` is a signed bundle containing a recipe, the matching skills, and (optionally) brand-kit overrides. A consumer fetches it, verifies the signature, presents the consent surface, and lets the user adopt it.

See [Marketplace → Publishing](/marketplace/publishing/) and [Marketplace → Consuming](/marketplace/consuming/).
