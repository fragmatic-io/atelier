The `ActionDispatcher` is the runtime surface that handles every capability dispatch. It owns the confirmation flow, the optimistic UI hook, the undo middleware integration, and the audit event firing.

## The interface

```ts
export interface ActionDispatcher {
  dispatch(input: DispatchInput): Promise<DispatchResult>;
}

export interface DispatchInput {
  capability_id: string;
  input: unknown; // Capability.input shape
  manifest_id: string;
  user_id: string;
  route: string;
  // ... audit-context fields
}

export interface DispatchResult {
  result: unknown; // Capability.output shape
  audit_id: string;
  duration_ms: number;
  optimistic: boolean;
}
```

## Confirmation flows

Capabilities declare `confirmation: 'none' | 'modal' | 'verbal_required'`. The dispatcher renders the matching surface:

| Confirmation      | UX                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `none`            | Dispatch immediately.                                                                             |
| `modal`           | Render `<ConfirmDialog>` portal; wait for OK / Cancel.                                            |
| `verbal_required` | Render `<ConfirmDialog>` with a verbal-phrase challenge ("type 'archive 47 threads' to confirm"). |

The portal lives in `@atelier/react`'s `<CirRuntime>` provider. Hosts don't render confirmation surfaces themselves — the dispatcher portals one in.

## Code: dispatching directly

```ts
import { ActionDispatcher } from '@atelier/runtime';

const result = await dispatcher.dispatch({
  capability_id: 'thread.archive',
  input: { thread_id: 't_xxx' },
  manifest_id: 'm_yyy',
  user_id: 'demo-user',
  route: '/today',
});
```

In React, components don't call `dispatch` directly. The walker maps a manifest node's `actions` array to the registered capability ids and wires `onPrimaryAction`, `onSecondaryAction`, etc. through to the dispatcher (principle #8: capability dispatch is first-class).

## Optimistic UI (Int-4)

`useOptimisticAction` from `@atelier/react` auto-wires for any capability with `reversible: true && low_stakes: true`:

```tsx
import { useOptimisticAction } from '@atelier/react';

function ThreadRow({ threadId }) {
  const onArchive = useOptimisticAction({
    capability: 'thread.archive',
    input: { thread_id: threadId },
    optimistic: (state) => ({ ...state, archived: true }),
  });
  return <Button onClick={onArchive}>Archive</Button>;
}
```

The hook:

1. Applies the optimistic update to local state immediately.
2. Calls the dispatcher in the background.
3. On success, the audit event confirms; the optimistic state stays.
4. On failure, the hook rolls back the optimistic state and surfaces an `<Alert>`.

For most reversible / low-stakes capabilities, the walker auto-wires this without authors writing the hook explicitly.

## Undo middleware (Int-8)

Wrap any dispatcher with `withUndo()`:

```ts
import { withUndo } from '@atelier/runtime';
import { createUndoToastEmitter } from '@atelier/react';

const undoEmitter = createUndoToastEmitter();

const dispatcher = withUndo(rawDispatcher, {
  emitter: undoEmitter,
  defaultWindowMs: 5000,
});
```

On every successful dispatch of a capability with `reversible: true && undoable: true`, `withUndo()` emits a toast event. The `<UndoToastSink>` renders it. See [Components → Undo toast](/components/undo-toast/) and [Runtime → Undo middleware](/runtime/undo-middleware/).

## Audit events

Every dispatch fires:

```text
action.requested      capability_id user_id manifest_id duration_ms=0
action.confirmed      (if confirmation flow ran)
action.dispatched     duration_ms=88
action.completed      audit_id=evt_xxx
```

If the dispatch fails:

```text
action.failed         reason='RateLimitExceeded' duration_ms=12
```

`<DebugPanel>` surfaces these events live; `pnpm atelier dev --tail` streams them to a terminal.

## Rate limiting

Capabilities declare `rate_limit: '100/min/user'`. The dispatcher's rate-limit middleware enforces this:

```ts
catch (err) {
  if (err.code === 'RATE_LIMIT_EXCEEDED') {
    return Response.json(
      { error: 'rate_limited', retry_after_ms: err.retry_after_ms },
      { status: 429 },
    );
  }
}
```

The runtime surfaces the limit via `<RateLimitChip>` (the inline remaining-quota indicator). The `rate_limited_actions_show_state` policy ensures the manifest exposes the chip.

## Error semantics

| Error                        | What happened                                             |
| ---------------------------- | --------------------------------------------------------- |
| `CapabilityNotFoundError`    | The capability id isn't in the registry.                  |
| `PermissionDeniedError`      | User doesn't hold the required permission.                |
| `RateLimitExceededError`     | Capability's rate limit blown.                            |
| `ConfirmationCancelledError` | User cancelled the modal / verbal challenge.              |
| `OptimisticRollbackError`    | Backend dispatched but returned an error; rollback fired. |

Hosts catch these in their error boundary and surface user-friendly messages.

## Composing dispatchers

```ts
import { withUndo, withRateLimit, withAudit } from '@atelier/runtime';

const dispatcher = withAudit(
  withRateLimit(withUndo(rawDispatcher, { emitter, defaultWindowMs: 5000 }), { capabilities }),
  { sink: auditSink },
);
```

Each wrapper is a pure function from `ActionDispatcher → ActionDispatcher`. Compose freely.
